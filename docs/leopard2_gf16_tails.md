# Leopard2 GF16 byte tails

## Scope and conclusion

Legacy Leopard GF16 arithmetic consumes 64-byte ALTMAP tiles.  Each tile is 32
GF(2^16) symbols stored as

    low(symbol 0)..low(symbol 31), high(symbol 0)..high(symbol 31).

The legacy API requires the byte count to be a multiple of 64, so it has no
wire representation for a partial tile.  The new API can extend that layout
without changing any complete legacy tile, but only when the application tail
contains a whole number of GF16 symbols.

For a residual application tail of `r = 2q` bytes, where `0 <= q < 32`, define
the compact ALTMAP extension as follows:

    application tail [ 0 .. q-1 ]       -> ALTMAP low  [ 0 .. q-1 ]
    application tail [ q .. 2q-1 ]      -> ALTMAP high [ 32 .. 32+q-1 ]
    every other byte in the 64-byte tile -> zero

Recovery output uses the inverse gather.  Complete 64-byte tiles remain byte
for byte identical to legacy ALTMAP.  Because packing and gathering retain both
bytes of every active GF16 symbol, an unchanged GF16 generator-matrix row acts
on the compact tail exactly as it acts on a full tile.  Shortened lanes are zero
and remain independent of active lanes.  Thus every even byte length has a safe
in-profile implementation, including lengths that are not multiples of 64.

The tempting alternative of copying an arbitrary prefix into an ALTMAP tile,
zero filling the suffix, and transmitting the same prefix of each parity tile
is not this construction.  It can retain low bytes while dropping the high
bytes generated by GF16 multiplication.  The projected code is not generally
MDS.

## Why odd lengths cannot be promised for all GF16 codes

This is an alphabet limitation, not a SIMD-tail implementation problem.
Suppose the public contract accepts `B = 1`, keeps each transmitted shard at
exactly one byte, is systematic, and reconstructs from every `K` of the `K+R`
coordinates.  It is then an MDS code over an alphabet of size 256, irrespective
of whether its implementation temporarily uses GF16.

Consider the legal low-profile counts `K = 2`, `R = 256`.  The public code would
have length 258 over the 256-element byte alphabet.  After fixing the two
systematic coordinates, every parity coordinate is a Latin square of order 256;
the ability to recover from every pair of coordinates requires all 256 parity
coordinates to be mutually orthogonal.  At most `q - 1 = 255` mutually
orthogonal Latin squares of order `q` can exist.  For completeness, relabel the
symbols of every square so that its first row is `0,1,...,q-1`.  The entry at
row 1, column 0 is nonzero in every square.  Two squares cannot use the same
entry `a` there, because their ordered pair `(a,a)` would occur both at row 1,
column 0 and at row 0, column `a`, contradicting orthogonality.  Those entries
are therefore distinct members of a set of only `q-1` nonzero symbols.
Therefore a byte-alphabet systematic `[258,2]` MDS code cannot exist.

This argument rules out a universal odd-tail promise under fixed `B`-byte shard
semantics.  It does not say that every individual small `(K,R)` projected code
fails, nor does it rule out a separately specified hybrid code in a smaller
region.  It says that the production GF16 profile cannot honestly meet the new
API's arbitrary-positive-length requirement for all otherwise legal counts
while emitting only `B` bytes per coordinate.

The direct test in `tests/leopard2/test_gf16_tails.cpp` strengthens the counting
argument with an executable witness.  It constructs the independent scalar
GF16 generator for low V1 `(K,R)=(2,256)`, projects each GF16 symbol to the low
byte exactly as prefix truncation would, and finds two transmitted coordinates
whose 16-by-16 binary recovery matrix is singular.  It produces a nonzero pair
of source bytes that is indistinguishable from the all-zero pair at those two
received coordinates.  The same test verifies compact even tails by direct
GF16 encoding and recovery rather than by calling optimized transforms.

## Required API and profile behavior

The production-safe behavior is:

1. Keep complete 64-byte GF16 tiles unchanged.
2. Accept even positive byte lengths by compactly scattering and gathering the
   final `2q` bytes as defined above.
3. Return `LEO2_UNSUPPORTED` for odd byte lengths in the current GF16 profiles.
   Scratch-size queries and execution calls must agree.
4. Continue to accept every positive byte length in GF8 profiles.
5. Document the GF16 two-byte execution granularity in public API and wire
   identity documentation.  This is a relaxation of a previously invalid byte
   length, not a change to any legacy-valid codeword.

If odd lengths are mandatory, one of these explicit designs is required:

- add one wire padding byte per shard and expose `wire_shard_bytes = B + 1` for
  odd `B`; the pad byte is part of every transmitted coordinate even if the
  caller's payload view hides it;
- introduce a separately identified GF8 or hybrid-tail profile, limited to a
  coordinate range for which its byte-alphabet MDS proof holds; or
- introduce an explicitly paired-batch profile that combines tails from two
  codewords and requires compatible erasure patterns.

None of these may be selected silently by a CPU backend or hidden behind the
current GF16 profile identifier.  In particular, using GF8 for the last byte is
not a GF16 wire-compatible kernel choice: the field, generator matrix, legal
coordinate count, and persistent code identity all differ.

## Validation obligations for the even-tail implementation

Before enabling compact tails in production:

- compare every even byte length 2 through 64, and 1024, against the independent
  scalar GF16 generator;
- cover both high and low coordinate profiles, direct and specialized decoders,
  every available backend, and generic-decoder differential checks;
- exercise the boundary lengths 2, 32, 34, 62, 64, 66, 1024, and 1026;
- verify all `K`-coordinate subsets in a small direct-oracle profile;
- verify complete 64-byte tiles remain byte-identical to old Leopard;
- run guard-page or canary checks plus ASan and UBSan; and
- retain odd-length rejection tests at 1, 3, 33, 63, 65, 1023, and 1025.

The compact scatter/gather must occur only in caller-to-scratch and
scratch-to-caller staging.  The GF16 FFT, multiplication, locator, and decode
kernels continue to receive full 64-byte ALTMAP tiles, so backend arithmetic and
wire coefficients do not change.
